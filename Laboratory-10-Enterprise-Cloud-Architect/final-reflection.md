# Final Reflection: From Junior Trainee to Enterprise Cloud Architect

Throughout Laboratories 1 to 10, my understanding of cloud computing changed from thinking that it was just about storing files online to understanding how different technologies work together to build and manage an infrastructure. I learned that the cloud involves more than storage. It can include virtual machines, networking, databases, containers, automation, and security. Each laboratory helped me understand how these components connect and how they can be used to create a working system.

One of the most challenging concepts for me was working with Docker and Docker Compose. At first, I found it difficult to understand how containers, images, networks, and volumes work together. However, when I deployed WordPress and MySQL using Docker Compose, I started to understand their purpose. WordPress handled the website, while MySQL stored the database. Docker Compose made it easier to start and manage both services using a configuration file instead of running many separate commands. I also learned that checking container status and reading logs are important when troubleshooting problems. Configuring the UFW firewall with a default-deny policy in this mission also reinforced a lesson from Laboratory 8 — that security should be built in from the start, not added afterward, since a single misstep in firewall order can lock out even the administrator.

What surprised me most in Laboratory 10 was having to work with less step-by-step guidance. In the earlier activities, I could follow instructions to complete each task. This time, I needed to think more carefully, understand error messages, and find solutions on my own. I encountered problems with missing directories, GitHub commands, file paths, and connecting to services. These issues were frustrating at first, but they taught me that errors are part of the learning process. I realized that becoming a cloud professional requires patience, problem-solving skills, and the ability to research unfamiliar problems.

If I were building this infrastructure for a real client, I would improve its security, reliability, and scalability. I would use strong passwords, protect database credentials, configure proper firewall rules, and enable HTTPS. I would also establish regular database backups and monitoring to detect problems early. For a larger business, I would consider using a managed database service, automated deployment, and cloud infrastructure that can scale when the number of users increases.

Overall, these ten laboratories helped me become more confident in working with cloud technologies. I know that I still have a lot to learn, but I now have a better understanding of how infrastructure components work together. My biggest lesson is that being an enterprise cloud architect is not only about knowing commands and tools. It is also about understanding the needs of users, solving problems, and designing systems that are secure, reliable, and practical.
